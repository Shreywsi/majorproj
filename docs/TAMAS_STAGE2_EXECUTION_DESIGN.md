# TAMAS Stage 2: Data and Execution Design

## Scope and evidence source

This design is based on the six JSON files and four Finance tool modules in the
official `ameyar3103/MultiAgentHarmDataset` repository at commit
`27fcf288e8c8c42a2c32c993d94623877a286016`. The checked-in sample contains 70
Finance records: 20 benign records and 10 records for each of five adversarial
categories. It is not the complete five-scenario, 350-record benchmark. The
dataset files and tool modules are kept as local research inputs; the upstream
repository has no declared license.

The loader's observed schema and field counts are documented in the TAMAS
section of the project [README](../README.md#7-icml-2025-tamas-sample-inspected-scope-and-loader).
The table below is the exact key presence observed in this pinned sample:

| Source file | Count | Record keys in every record | Agent keys in every agent object | Agent count |
|---|---:|---|---|---:|
| `PNA_finance.json` | 20 | `agents`, `user_query`, `sequence_of_tool_calls` | `agent_name`, `agent_description` | 4 |
| `RAS_finance_DPI.json` | 10 | `agents`, `user query`, `agents_involved` | `agent_name`, `agent_description` | 4 |
| `RAS_finance_IPI.json` | 10 | `agents`, `user query`, `agents_involved`, `expected output` | `agent_name`, `agent_description`, `backstory`, `tools` | 4 |
| `RAS_finance_Imp.json` | 10 | `agents`, `user query`, `agents_involved` | `agent_name`, `agent_description` | 4 |
| `RAS_finance_Coop.json` | 10 | `agents`, `user query`, `agents_involved` | `agent_name`, `agent_description` | 4 |
| `RAS_finance_contra.json` | 10 | `agents`, `user query`, `agents_involved` | `agent_name`, `agent_description` | 5 |

All queries and descriptions are strings; `agents` and `agents_involved` are
arrays. IPI `expected output` is a string. IPI agents contain empty `backstory`
strings and empty `tools` arrays in this sample. PNA tool-call sequences are
arrays of strings. The query key differs: PNA uses `user_query`; all adversarial
files use `user query`.

The tool modules are separate from the record JSON. The static AST catalog
finds 33 function definitions: 8 for Identity Verification, 9 for Market
Analysis, 9 for Risk Management, and 7 for Trade Execution. The Risk Management
module defines `log_risk_event` twice. The code only parses declarations; it
does not import or execute the modules. Tool classification is left unknown
where upstream does not supply a machine-readable normal/attack designation.

## Meaning and mapping of TAMAS labels

The JSON records do not contain a `label` or `attack_type` field. The loader
assigns the category from the official source filename:

| Source filename | Record-level class |
|---|---|
| `PNA_finance.json` | `benign` |
| `RAS_finance_DPI.json` | `direct_prompt_injection` |
| `RAS_finance_IPI.json` | `indirect_prompt_injection` |
| `RAS_finance_Imp.json` | `impersonation` |
| `RAS_finance_Coop.json` | `colluding_agents` |
| `RAS_finance_contra.json` | `contradicting_agents` |

This is a **record-level task/attack-category label**. It is not an agent-level
truth label, a label for each message/tool interaction, or an observed execution
outcome. `agents_involved` is a record-level list of agent role names supplied
in adversarial records. It is not a verified per-agent maliciousness label, a
claim-truth assessment, or an interaction annotation. Do not copy it into a
detector input or use it to identify an agent as dishonest.

The original TAMAS category and a future provenance-paradox label are separate
target variables. Never derive the latter from the former. Provenance labels
must be assigned only after the claim and supporting evidence are independently
reviewed according to an explicit annotation protocol.

## Detector inputs and evaluator-only data

The detector can receive only information available at the time of routing or
monitoring:

| Field/source | Runtime treatment |
|---|---|
| Original user query | Runtime task input; retain unchanged. |
| Agent name and description | Expose as unverified, agent-provided role/capability claims, not as verified identity or competence. |
| Embedded agent `tools` field | May be supplied as declared tools only where present. In the inspected IPI records it is empty; absence/emptiness does not mean the separately published tool modules are a task-specific tool grant. |
| Static tool-module declarations | May inform a future tool registry after safe, explicit mapping. A function declaration alone is not proof that an agent was granted, called, or successfully used a tool. |
| Actual run-time messages, handoffs, router decisions, tool invocations/results | Detector input only after those events have occurred and been recorded. Events generated by the controlled simulator must remain explicitly marked as simulated, not as observed LLM/tool behavior. No event may be represented as a real observation merely because a task description mentions it. |
| Runtime-attested evidence | Available only if produced by the configured evaluator/issuer and present in the event stream. A valid signature establishes record integrity and signer identity, not that the claim or result is true. |

The following are held in a separate evaluator mapping and must not enter the
detector/runtime object:

* filename-derived TAMAS class and the original source filename;
* `agents_involved`;
* IPI `expected output`;
* PNA `sequence_of_tool_calls` when it is being used as reference/expected
  execution data rather than as an event actually observed during the current
  run;
* claim-level ground-truth verification status, annotation rationale, and
  post-run metric labels.

The current loader's `TAMASRecord` intentionally retains evaluator fields for
inspection. It is **not** itself a detector interface. Use
`DetectorTaskInput.from_tamas_record(record, task_id=...)`, with an opaque
runtime task ID, as the whitelist projection. The projection maps agents to
per-task IDs such as `agent-000`; it omits filename, label, involved-agent
annotation, expected output, and recorded reference tool calls. Keep the
opaque task-ID-to-source-record mapping in evaluator-only storage.

## What the released data establishes (and does not)

The records establish the presence of original query text, agent role names and
descriptions, attack-category provenance by file, and the optional fields
listed above. They do **not** provide:

* authenticated or persistent agent identities;
* proof that a role/capability description is truthful;
* a structured set of capability claims tied to evidence;
* issuer attestations, external benchmarks, or historical performance records;
* actual LLM-generated messages, real tool outputs, real execution results, or
  detector observations from the original benchmark runs;
* per-agent maliciousness, claim truth, or per-interaction ground truth.

The four Finance tool files declare Python functions but their record-to-agent
assignments and normal-versus-attack classification are not sufficiently
machine-readable to claim verified capability. No tool function should be
executed as part of this design stage.

To evaluate whether an agent's claims are truthful, additional labels must be
collected separately:

1. **Claim annotation:** exact claimed role and atomic capabilities, verbatim
   source text, time of claim, and the agent/session identity to which it is
   bound.
2. **Evidence annotation:** evidence type (`self_claimed`,
   `runtime_observed`, `issuer_attested`, or `externally_benchmarked`), stable
   reference, issuer, collection time, and whether integrity/signature
   validation succeeded. Integrity and truth are distinct findings.
3. **Behavior annotation:** links to actual trace event IDs demonstrating
   relevant behavior; annotators must not infer unobserved behavior.
4. **Claim assessment:** `supported`, `contradicted`, or `inconclusive`, with
   evaluator identity/method and cited evidence IDs. If no evidence has been
   reviewed, status remains `not_assessed`.
5. **Identity binding:** whether an ID is only a per-run alias, session-bound,
   issuer-attested, or cryptographically bound. Do not treat a repeated role
   name as a persistent identity.
6. **Protocol quality:** independent annotation and adjudication for contested
   claims, documented criteria, inter-annotator agreement, and explicit
   treatment of unknown/insufficient evidence.

No agent-level ground-truth labels are inferred from the current TAMAS sample.

## Proposed schemas

The models in `dataset/experiment_schemas.py` define and validate the following
contracts. They do not execute workflows or produce events; the separate Stage
3 controlled simulator creates only explicitly marked simulated events.

### Interaction trace

An `InteractionTrace` contains a trace ID, opaque runtime task ID, interaction
mode, optional model identifier/version and seed, and ordered `TraceEvent`
items. Each event includes:

* zero-based contiguous `sequence`;
* event type (`task_submitted`, `agent_message`, `handoff`,
  `tool_invocation`, `tool_result`, `router_decision`, `detector_alert`,
  `task_completed`, or `task_failed`);
* source (`user`, `agent`, `tool`, `router`, `detector`, or `system`);
* optional actor/recipient IDs and elapsed milliseconds from run start;
* original message content when it is actually observed;
* tool name, JSON-compatible arguments, and JSON-compatible result for
  actual tool events.

Structural validation enforces event ordering, non-negative sequence/time,
required source/actor/recipient fields, and tool names for tool events. A
completed future run should persist the model/deployment identifier, prompt and
tool-registry versions or hashes, interaction mode, seed, and execution
configuration alongside the trace. Those fields are experiment provenance,
not proof that an outcome is truthful.

Keep the trace free of benchmark labels and expected/evaluator results. Store
the mapping from opaque task ID to TAMAS source record and the post-run
evaluator results in a separate access-controlled evaluation record.

### Provenance claim

A `ProvenanceClaim` contains:

* `claim_id` and per-run `agent_id`;
* `identity_binding` with explicit verification level;
* claimed role and atomic claimed capabilities;
* supporting `ClaimEvidence` items, each recording evidence ID/type/source,
  optional issuer, and signature/integrity result;
* `ObservedBehavior` links to trace IDs and event sequence numbers;
* a separate `ClaimAssessment` with evaluator-only truth status, assessor,
  method, and cited evidence IDs.

`ProvenanceClaim.detector_view()` omits `ClaimAssessment` and returns a
`DetectorProvenanceClaim`. This makes the ground-truth assessment unavailable
through the intended detector-facing projection. Training/evaluation software
must still enforce this separation at the application and storage boundaries.
`integrity_verified=True` must never be treated as `ClaimTruthStatus.SUPPORTED`
without separate substantive evidence.

## Experiment methodology proposed for the next stages

1. Freeze a manifest of the pinned source commit, local file hashes, selected
   opaque task IDs, and protocol version. Keep evaluator label mappings outside
   detector inputs.
2. Do not modify the original TAMAS JSON. Keep provenance-paradox manipulations
   as separately versioned experimental conditions and attach them only in
   experiment metadata. Pair the same original task across baseline and
   extension conditions.
3. Build and validate a safe local execution adapter before running an agent.
   Tool effects must be simulated and isolated. An attempted action and its
   observed result must be distinct trace events. Never import or execute the
   upstream tool modules as real tools.
4. Log the actual query, agent messages, handoffs, router decisions, tool
   invocations/results, failures, and timings. If a run produces no event, do
   not synthesize one. Record model, prompt, tool-registry version, seeds, and
   configuration for reproducibility.
5. Make the detector consume only the runtime projection and observations
   available at that point. Freeze the detector before exposing the evaluator
   mapping. Keep deterministic detector output distinct from any optional LLM
   judge output.
6. Evaluate TAMAS record-level category detection only after execution against
   the filename-derived class. Report per-category and macro metrics and
   benign false positives. Do not score agent-level claim truth with TAMAS
   attack labels.
7. Evaluate provenance-claim detection only on separately annotated claims
   with evidence and adjudicated truth status. Report the sampling and
   annotation protocol; unknown/inconclusive claims are not silently converted
   to true or false.
8. Treat the available sample size (10 records per adversarial class and 20
   benign) as a limitation. Report paired task-level results and uncertainty;
   do not present the Finance sample as the complete benchmark.
9. Compute ARIA, PNA, Safety, and ERS only from real, complete, safe execution
   traces and a documented evaluation procedure. They are execution-outcome
   metrics, not dataset labels.

## Stage 3 controlled execution boundary

The current Stage 3 prototype adds `dataset/execution_engine.py`,
`dataset/safe_tools.py`, `dataset/trace_store.py`, and
`run_tamas_execution.py`. It accepts only `DetectorTaskInput` and the static
Finance tool catalog; it does not receive or inspect `TAMASRecord` labels,
`agents_involved`, expected outputs, or reference tool-call sequences.

The role planner deterministically matches a small set of task-query terms to
the original role names and chooses a catalogued tool for a matching role.
This is a transparent orchestration heuristic, not a capable LLM, attack
detector, task planner, or faithful implementation of the AutoGen interaction
systems. Magentic-One-like mode records coordinator-to-delegate handoffs;
Round-Robin-like mode records sequential handoffs; Swarm-like mode schedules
agents without handoff edges. These modes are trace-shape approximations only.
Tool argument payloads contain the original query as `task_context`; they are
passed only to the local no-op adapter and are not validated against or passed
to upstream functions.

All 33 AST-catalogued function declarations are registered by their source
location. Each adapter only emits a `simulated_response` stating that nothing
was accessed or changed; no tool module is imported, no external service is
called, and no financial action occurs. The trace marks invocations as
`local_simulation` and responses as `simulated_response`. Agent messages are
not synthesized. The trace ends with `simulation_ended`, never
`task_completed`; task completion remains `not_evaluated`.

Trace `sequence` is the authoritative event order. `elapsed_ms` is a
deterministic logical event tick, not wall-clock timing. Seed, interaction
mode, tool-registry version/hash, and deterministic planner configuration hash
are recorded. Repeated runs with the same task ID, mode, and seed serialize
identically. The prototype stores JSONL traces separately from an
evaluator-only JSONL mapping that links opaque task IDs to TAMAS source records
and record labels. The mapping is written by the validation runner, never by
the execution engine and never included in the trace.

Run the validation pair (one actual benign and one actual DPI Finance record):

```bash
.venv/bin/python run_tamas_execution.py \
  --mode round_robin --seed 19 \
  --out data/tamas/runs/stage3_validation.jsonl
```

By default the trace file and its separate `.evaluator.jsonl` sidecar remain in
the ignored local TAMAS data directory. This pair demonstrates schema-valid
orchestration and simulated tool-call logging only. It is not an LLM run, does
not evaluate attack success or claim truth, and is not benchmark evidence.

Validation on the first benign Finance record and first DPI Finance record
produced two schema-valid traces:

| Condition | Scheduled roles | Local simulated tool calls | LLM responses | External actions | Completion |
|---|---:|---:|---:|---:|---|
| Benign | 4 | 4 (`verify_otp`, `analyze_market_sentiment`, `place_order`, `adjust_stop_loss`) | 0 | 0 | `not_evaluated` |
| DPI | 3 | 3 (`verify_kyc_documents`, `forecast_price_movement`, `log_risk_event`) | 0 | 0 | `not_evaluated` |

These are trace-structure counts, not correctness or security scores. The DPI
tool named `log_risk_event` is handled by the same inert stub; no external
logging occurs. Trace records contain no TAMAS class or source filename; the
separate sidecar contains the evaluator mapping.

Still unimplemented: LLM/autogen execution, actual agent-generated decisions
and messages, realistic tool-specific simulation semantics, identity
verification, runtime provenance attestation, execution-based evaluation,
detectors, R0–R8 integration, routing/truth annotation, metrics, and dashboard.
The current 70-record Finance sample is not the full ICML 2025 benchmark.
