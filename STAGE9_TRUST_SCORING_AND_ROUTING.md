# Stage 9 Trust Scoring and Routing

## Runtime boundary

The Stage 9 router accepts a `RoutingTask`, a tuple of `AgentCandidate` runtime
profiles, and a mapping of detector-derived `AgentTrustHistory` records. These
types contain no behavior label, expected value, evaluator sidecar, task result,
or TAMAS label. The experiment controller chooses before generating the task,
then supplies only runtime messages, signed evidence, Stage 4 findings, and
Stage 7D cross-message findings to history updates. The independent evaluator
joins sidecars only after the full routing sequence is complete.

The optional Stage 7C routing extension changes only the operator slot and
stable roster/key namespace when explicitly requested. Default Stage 7C runs
retain task-local identities, the original operator, and existing experiment
IDs. Stage 9 uses one task per generated experiment because the identity
registry binds registrations at task scope.

## Trust score

For an agent's prior detector history:

* `R = (SUPPORTED + 1) / (SUPPORTED + CONTRADICTED + 2)`
* `E = (valid evidence references + 1) / (all verification-status references + 2)`
* `I = (verified identity checks + 1) / (identity checks + 2)`
* `X = (cross-message task checks - tasks with findings + 1) / (checks + 2)`
* `C = assertions with at least one valid evidence association / evaluated assertions`

An unobserved evidence, identity, cross-message, or coverage component has the
neutral prior `0.5`. Evidence coverage is reported as unavailable when no
assertions have been evaluated. The default configurable weights are:

`raw = 0.40 R + 0.20 E + 0.15 I + 0.15 X + 0.10 C`

With `n` prior evaluated assertions and a minimum-observation constant of 3:

`confidence = n / (n + 3)`  
`score = 0.5 + confidence * (raw - 0.5)`

The cold-start flag is true while `n < 3`; a new agent receives a neutral score
of `0.5`, not automatic rejection. Unsupported and insufficient-evidence
outcomes remain separate history counts and do not enter `R` as false
assertions. Only SUPPORTED and CONTRADICTED affect that component.
Evidence-verification failures affect evidence integrity/coverage, not
assertion truth. A valid signature authenticates the evidence record; it does
not prove an assertion objectively true.

The score is an operational ranking signal, not a probability that an agent is
honest and not a malicious-agent label. One assertion does not blacklist an
agent. The history contains only observations completed before the current
decision.

## Capability-gated routing

1. Remove candidates that are not eligible for the required role, do not
   declare the required capability, or have a current runtime identity-binding
   mismatch.
2. A verified capability demonstration is preferred ahead of trust score.
   For a local-simulation task, a verified simulated demonstration can qualify
   only as a **simulated** demonstration. For an external task, only an
   `actual_demonstration` record can qualify. No external tasks or evidence are
   generated by this corpus.
3. If no eligible candidate has a relevant verified demonstration, use the
   declared-permission cold-start fallback; permission alone is not represented
   as demonstration.
4. Within the best compatible capability tier, select the highest smoothed
   trust score. Resolve exact ties by stable agent ID.
5. Persist eligible and excluded candidates, exclusion reasons, each score and
   component, detector-history counts, capability compatibility, evidence
   coverage, selected agent, sequence, and rationale.

Configured permission is available to the controlled runtime as a candidate
declaration, but it never becomes a capability demonstration. Capability
history is built only from signed runtime tool evidence that is validly
associated with a demonstrated-capability assertion. Local tool events retain
their `LOCAL_SIMULATION` status.

## Legacy baseline adapter

The existing `router.py` R0–R8 algorithms were not changed. The Stage 9
runner invokes each existing `Router` version on the same five-agent,
five-scenario controlled task sets. Because the original router API consumes
numeric profiles and reward observations rather than structured provenance,
the adapter maps:

* R0 to its original random selection.
* R1 to the smoothed rate of prior self-reported `RECORDED` tool-execution
  claims.
* R2–R8 to their original policy logic, updated with a system-attested scalar
  summary of prior Stage 4 outcomes: SUPPORTED=1, CONTRADICTED=0, and
  UNSUPPORTED/INSUFFICIENT_EVIDENCE=0.5.

The attestation proves that the supplied scalar is the controller's
detector-derived observation; it is not an independent evaluator label or
objective truth. Legacy policies receive the same runtime roster, task
requirements, detector history, and profile observations at decision time;
they consume only the input signals their unchanged algorithm defines. Stage 9
is therefore an adapter-based comparison, not a claim that the original
continuous-reward R0–R8 benchmark has been reproduced as a claim-bearing
system.

## Fixed assumptions and limits

* Default weights are fixed in code and were not tuned on the evaluation data.
* Five seeds rotate the scripted behavior-to-agent-slot assignment and scenario
  order. They are paired controlled configurations, not independent stochastic
  trials.
* All five agents participate in each generated task; only the assigned
  operator slot changes. The tasks are deterministic local simulations.
* Four scenarios always complete and `missing_lookup` always returns
  `found=false`; task success is scenario-defined and does not depend on the
  selected behavior. Routing cannot improve the task-success rate in this
  experiment design.
* No routing-decision latency is reported; timing was not measured reliably.
* TAMAS has no claim-bearing conversations or per-agent truth, so it cannot
  supply trust histories or a trust-aware routing evaluation.
